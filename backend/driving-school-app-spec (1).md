# مواصفات مشروع: تطبيق مدرسة تعليم قيادة

> هذا الملف خلاصة نقاش تصميمي كامل (قبل كتابة أي كود) بين صاحب المشروع ومساعد. جميع القرارات هنا **نهائية ومحسومة** ما لم يُذكر خلاف ذلك صراحة. يُستخدم هذا الملف كسياق كامل لأداة أكواد (Claude Code أو ما شابه) للبدء بالتنفيذ.

## 1. الفكرة العامة

تطبيق لمدرسة تعليم قيادة سيارات، فيه ثلاث أقسام رئيسية:
1. **حجوزات وجدولة دروس** بين الطالب والمدرب.
2. **محتوى تعليمي** (فيديوهات/صور) وكويزات مرتبطة به.
3. **تتبع تقدم الطالب** بالمهارات العملية.

**قرار معماري أساسي:** التطبيق مبني من اليوم الأول على بنية "مدرسة فيها أكثر من مدرب"، لكن **الإصدار الأول (v1)** سيُشغَّل بمدرب واحد فقط (العميل الحالي). لاحقاً، بدون إعادة بناء قاعدة البيانات، يمكن فتح شاشات إدارة المدربين المتعددين وبيع النظام كمنتج مدرسة كامل. السبب: بنية قاعدة البيانات مكلفة التغيير لاحقاً، بينما إخفاء/إظهار ميزات في الواجهة رخيص.

## 2. الأدوار (Roles)

| الدور | الوصف |
|---|---|
| **Admin** | يملك النظام كامل، يدير المدربين والمشرفين والإعدادات العامة، يقدر يرفع محتوى تعليمي، عنده لوحة إحصائيات عامة |
| **Supervisor (مشرف)** | يدير الحجوزات، يعتمد/يرفض أوقات توفر المدربين، يعيّن المدرب المناسب للطالب عند الحجز، ينفّذ الإلغاء (بما فيه الإلغاء نيابة عن المدرب)، يؤكد الدفعات يدوياً، يرد على رسائل الطلاب، يقدر يرفع محتوى تعليمي |
| **Instructor (مدرب)** | يقترح أوقات توفره الأسبوعية (تحتاج اعتماد المشرف)، يعطي الدروس، يقيّم مهارات طلابه، عنده لوحة خاصة بجدوله اليومي وطلابه |
| **Student (طالب)** | يطلب حجز، يشاهد المحتوى التعليمي ويحل الكويزات، يتابع تقدمه بالمهارات، يراسل المشرف فقط (لا يوجد تواصل مباشر مع المدرب داخل التطبيق). كل الطلاب من نفس النوع، لا توجد مستويات مختلفة |

## 3. دورة حياة "وقت توفر المدرب" (Availability Slot)

```
مقترح (proposed) → المشرف يراجع → معتمد (approved) → يصير قابل للحجز
                                → مرفوض (rejected) → يرجع للمدرب مع السبب
```

المدرب لا يستطيع فرض أي وقت مباشرة على النظام؛ لازم اعتماد المشرف أولاً.

## 4. دورة حياة "الحجز" (Booking)

```
الطالب يطلب حجز → المشرف يعيّن المدرب (من الأوقات المعتمدة) → الحجز مؤكد
                                                              → تم الدرس (completed)
                                                              → تم الإلغاء (cancelled)
```

الطالب لا يختار المدرب بنفسه — المشرف هو من يعيّن المدرب المناسب لكل طلب حجز.

### قيد نوع الغيار (عادي/أوتوماتيك)
- كل طالب يحدد نوع الغيار (`manual` أو `automatic`) **مرة واحدة عند التسجيل**، وثابت لكل دروسه بعدها.
- كل مدرب ممكن يدعم النوعين مع بعض (عنده سيارتين).
- **قاعدة إجبارية عند التعيين:** المشرف لازم يختار مدرب يدعم نفس نوع الغيار اللي حدده الطالب — وإلا التعيين غير صالح.

### قاعدة إلغاء الحجز
- يوجد **مدة سماح** (قابلة للتعديل من الإعدادات، ليست مكتوبة داخل الكود).
- إلغاء خارج مدة السماح → غرامة = **نصف سعر الدرس**. ضمن مدة السماح → بدون غرامة.
- إذا أراد **المدرب** الإلغاء → يطلب من المشرف، **والمشرف هو من ينفّذ الإلغاء فعلياً**.

## 5. التسعير والدفع

- سعر الدرس **ثابت للجميع** (لا يختلف حسب المدرب أو نوع الدرس)، يُخزَّن كإعداد عام قابل للتغيير.
- **كل حجز يخزّن السعر (`price`) وقت إنشائه** كـ"لقطة" (snapshot)، لا يُحسب لاحقاً من الإعداد الحالي، لمنع تغيّر سعر حجوزات قديمة إذا تغيّر السعر العام.
- **طرق الدفع في v1:**
  1. **نقدي** — تسجيل يدوي.
  2. **شام كاش (QR)** — التطبيق يولّد رابط/QR يفتح شام كاش على حساب المدرسة. لا يوجد تكامل API حقيقي، فتأكيد استلام الدفعة **يدوي** من المشرف/الأدمن.
  - الطريقتين تُعاملان بنفس الشكل من ناحية قاعدة البيانات: حالة دفع تحتاج تأكيد يدوي.

## 6. المحتوى التعليمي

- الفئات (نظري، إشارات، قطع السيارة، نصائح عامة...) **ديناميكية**، الأدمن/المشرف يضيفوها ويعدّلوها وقت ما بدهم.
- كل فئة تحمل خاصية **`is_sequential`**: لو `true` (متل دروس القيادة الأساسية)، المحتوى يُشاهَد بالترتيب الإجباري. لو `false` (متل الإشارات والنصائح)، تصفح حر.
- كل محتوى ممكن يكون له كويز اختياري.
- **قاعدة الكويز:** لو الفئة متسلسلة، لازم اجتياز الكويز لفتح المحتوى التالي. لو غير متسلسلة، الكويز للمراجعة فقط بدون شرط.
- **محاولات الكويز غير محدودة** (الطالب يعيد لحد ما ينجح).
- الأدمن **والمشرف** كلاهما يقدر يرفع محتوى (وليس الأدمن فقط).
- المشرف/المدرب عندهم **لوحة تقدم** تعرض أي محتوى شافه كل طالب وعلامته بالكويز.

## 7. تتبع المهارات العملية

- قائمة المهارات (ركن متوازي، طريق سريع...) **قابلة للتعديل من الأدمن** وقت ما بده، وليست ثابتة بالكود.
- شكل التقييم: **ثنائي** (منجزة / غير منجزة)، وليس تدريج.
- التقييم **مستقل عن الحجوزات** — المدرب يحدّثه متى ما بده، بدون ربط إجباري بحصة معينة.
- **ميزة مستقبلية سهلة بدون تعديل بنية:** شهادة إتمام (استعلام بسيط: هل كل مهارات الطالب منجزة؟).

## 8. لوحات التحكم

| اللوحة | المحتوى |
|---|---|
| **الأدمن** | إحصائيات عامة (عدد الطلاب، الدخل، الحجوزات) + إدارة المدربين والمشرفين (إضافة/حذف) |
| **المشرف** | شاشة يومية واحدة تجمع: الحجوزات اليومية/القادمة + طلبات اعتماد أوقات التوفر المعلّقة + دفعات بحاجة تأكيد يدوي |
| **المدرب** | جدوله اليومي وطلابه فقط (منفصلة تماماً عن لوحتي الأدمن والمشرف) |

> ملاحظة هندسية: ولا لوحة من الثلاث تحتاج جدول جديد بقاعدة البيانات — كلها "طرق عرض" مختلفة على نفس الجداول الأساسية حسب الدور.

## 9. الإشعارات والتواصل

- **إشعارات تلقائية** (تأكيد حجز، تذكير، إلغاء...) عبر نظام Laravel Notifications:
  - v1: داخل التطبيق (جرس إشعارات) + إيميل.
  - v2 (لاحقاً): إشعار push حقيقي عبر Firebase — يتأجل لحاجته لتنسيق مع مطور الفلاتر. بما إنه نظام الإشعارات مبني على قنوات قابلة للإضافة، لن يحتاج إعادة بناء.
- **دردشة حرة:** فقط بين **الطالب والمشرف/الأدمن**. **لا يوجد تواصل مباشر بين الطالب والمدرب** داخل التطبيق إطلاقاً.

## 10. نموذج البيانات الكامل (Domain Model)

> أسماء وحقول مبدئية لتوضيح البنية والعلاقات، وليست migrations نهائية.

```
USERS
  id, name, email, password, role (admin | supervisor | instructor | student)
  transmission_type (manual | automatic) -- للطالب فقط، يُحدَّد عند التسجيل ولا يتغيّر
  teaches_manual, teaches_automatic (boolean) -- للمدرب فقط، يدعم واحد أو الاثنين

AVAILABILITY_SLOTS
  id, instructor_id (FK users), start_time, end_time, status (proposed | approved | rejected)

BOOKINGS
  id, student_id (FK users), slot_id (FK availability_slots), assigned_by (FK users, supervisor),
  price, status (pending | confirmed | completed | cancelled),
  cancelled_by (FK users, nullable), penalty_amount (nullable)

PAYMENTS
  id, booking_id (FK bookings), method (cash | sham_cash), amount,
  status (pending | confirmed), confirmed_by (FK users)

CONTENT_CATEGORIES
  id, name, is_sequential (boolean)

CONTENTS
  id, category_id (FK content_categories), uploaded_by (FK users: admin أو supervisor),
  title, type (video | image), url, order_index

QUIZZES
  id, content_id (FK contents), pass_score

QUIZ_QUESTIONS
  id, quiz_id (FK quizzes), question, options, correct_answer

STUDENT_CONTENT_PROGRESS
  id, student_id (FK users), content_id (FK contents), completed (boolean), quiz_score

SKILLS
  id, name

STUDENT_SKILLS
  id, student_id (FK users), skill_id (FK skills), is_completed (boolean),
  updated_by (FK users), updated_at

MESSAGES
  id, sender_id (FK users), receiver_id (FK users), body, read_at, created_at
  -- قيد: أحد الطرفين لازم يكون طالب، والآخر مشرف أو أدمن

SETTINGS (key-value، غير مرتبط بعلاقات)
  cancellation_grace_hours, cancellation_penalty_percent, lesson_price, ...
```

### العلاقات الأساسية
- `users` (instructor) 1—N `availability_slots`
- `users` (student) 1—N `bookings`
- `availability_slots` 1—N `bookings`
- `bookings` 1—N `payments`
- `content_categories` 1—N `contents` — `contents` 1—0/1 `quizzes` — `quizzes` 1—N `quiz_questions`
- `users` × `contents` → `student_content_progress` (جدول ربط)
- `users` × `skills` → `student_skills` (جدول ربط)
- `users` ↔ `users` عبر `messages` (طالب ↔ مشرف/أدمن فقط)

## 11. مبادئ هندسية تم اعتمادها أثناء التصميم

1. **فصل الاهتمامات (Separation of Concerns):** الحجز، الدفع، المحتوى، المهارات — كل واحد جدول/مجموعة جداول مستقلة بمسؤولية واحدة.
2. **الحالات كـ enum صريح (State Machine):** بدل booleans متفرقة، لكل من `availability_slots.status` و`bookings.status` و`payments.status` قيم محددة واضحة.
3. **الإعدادات القابلة للتغيير خارج الكود:** أي رقم/نسبة قابلة للتغيير من صاحب العمل (مدة السماح، نسبة الغرامة، سعر الدرس) في جدول `settings`، لا تُكتب مباشرة في الكود.
4. **لقطة البيانات وقت العملية (Data Snapshot):** أي قيمة مالية مرتبطة بعملية تُخزَّن وقت حدوث العملية، لا تُحسب لاحقاً من مصدر متغير.
5. **جداول الربط (Pivot Tables) لحمل بيانات إضافية:** `student_content_progress` و`student_skills` أمثلة على علاقات "كثير لكثير" مع بيانات إضافية على العلاقة نفسها.
6. **اللوحات = طرق عرض، لا جداول جديدة:** لوحات الأدمن/المشرف/المدرب كلها استعلامات مختلفة على نفس البيانات الأساسية.
7. **تصميم قابل للتوسع دون تغيير البنية:** دعم مدرسة كاملة من اليوم الأول، حتى لو الاستخدام الأول لمدرب واحد فقط.
8. **عدم الإفراط بالهندسة (Avoid Over-engineering):** ليس كل تصنيف يحتاج جدول منفصل ديناميكي — نوع الغيار (عادي/أوتوماتيك) قيمتين ثابتتين من واقع السيارات نفسه، فتم تمثيله بحقول بسيطة على `users`، بعكس فئات المحتوى التعليمي التي هي فعلاً مرشحة للتوسع المستمر.

## 12. التقنيات المقترحة (Suggested Stack)

- **Backend:** Laravel (API فقط، بدون Blade views) + Laravel Sanctum للمصادقة + Laravel Notifications
- **Frontend (ويب):** React + Vite
- **Mobile:** Flutter (يُبنى من شخص آخر، يستهلك نفس الـ Laravel API)
- **أدوات مجانية للتطوير:** Laravel Sail/Herd, Postman, GitHub
- **استضافة مجانية للتجربة:** Railway أو Render (backend), Vercel أو Netlify (React), Cloudinary (تخزين الفيديوهات/الصور)

## 13. ترتيب البناء المقترح

1. إعداد بيئة العمل محلياً (Laravel Sail/Herd + Node.js)
2. بناء الجداول والعلاقات (migrations) حسب القسم 10
3. بناء الـ API الكامل واختباره عبر Postman قبل لمس الرياكت
4. تعلّم أساسيات React بمشروع صغير منفصل
5. ربط ميزة واحدة فقط (تسجيل الدخول) بين React والـ Laravel API لفهم نمط الربط
6. إضافة الحجوزات، ثم المحتوى التعليمي، ثم المهارات، ثم اللوحات، ثم الإشعارات/الدردشة — تباعاً بنفس النمط
7. رفع المشروع أونلاين مجاناً للتجربة
